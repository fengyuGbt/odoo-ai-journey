# 学习路线图 · Roadmap

> 以 Odoo 工程为背景，把《动手学大模型》11 章变成"学一章、能在 ERP 上落一块"的学习路径。

## 核心思路

```
课程（模型原理与训练）
   │  判断力：该用什么方案、方案靠不靠谱
   ▼
LLM 工程（RAG / function calling / eval）   ← 课程没讲，但生产天天用
   │  工程力：把模型接进业务系统
   ▼
Odoo 业务（销售 / 采购 / 客服 / 财务 / 报表）
```

**一句话：课程 = 判断力，工程 = 生产力，Odoo = 场景。**

## 工程三件套（课程缺失，必须补）

| 技能 | 解决什么问题 | 在 Odoo 里对应 |
|---|---|---|
| RAG + 向量检索 | 模型"不知道"你的业务数据 | 读 PostgreSQL + 文档 → 检索增强回答 |
| Function calling | 模型只能说话、不能干活 | 封装 Odoo API 成工具，让模型调用 |
| Eval 测试集 | 不知道 agent 改好还是改坏了 | 风险/质量测试用例模型 + 回归 |

详见 [`11-engineering-toolkit.md`](11-engineering-toolkit.md)。

### 工程第四件套：规则 × LLM 协同（hybrid extraction）

> 思路来源：正则的优势（快 / 免费 / 确定 / 可解释）不该被放弃；LLM 的优势（语义理解 / 覆盖自由表达）不该被它的弱点（慢 / 贵 / 不确定）拖累。**让规则管执行、LLM 管理解 + 管规则的维护**。

| 层 | 谁负责 | 说明 |
|---|---|---|
| 执行层 | 规则库（正则/模板） | 命中直接出结构化数据：微秒级、零成本、结果确定 |
| 理解层 | LLM | 未命中才调模型：语义理解，覆盖"客户不按规则说话" |
| 维护层 | LLM + 人审 | 成功样本 → LLM 生成候选正则 → **人工审一次入库** → 规则库越用越全，LLM 调用越来越少 |
| 质量门 | 回归测试集 | 每条规则配 ≥2 个真实样本，入库/改动必跑——否则规则静默误伤（**最易被忽略、最致命**） |

- **适用判断**：询盘量小、字段少 → 纯 LLM 即可（过度设计）；量大且表达多样 → 这套架构价值随"量 × 多样性"增长
- **Odoo 落点**：`lead_extractor` v2（规则快速通道 + LLM 兜底 + 样本沉淀）

## 学习阶段建议

### 阶段 1 · 立刻能用（第 1-2 周）
- 精读 Ch2（API 调用、零/少样本提示、CoT、self-consistency）
- Odoo 动手：`llm.service` 封装 + 产品描述自动生成按钮
- **里程碑**：Odoo 里能点一个按钮生成英文产品描述

### 阶段 2 · 补齐工程（第 3-6 周）
- 学工程三件套：RAG / function calling / eval
- 学工程第四件套：规则 × LLM 协同（hybrid extraction）
- Odoo 动手：`lead_extractor` v2 —— 规则快速通道 + LLM 兜底 + 样本沉淀 + 回归测试集
- Odoo 动手：自然语言查客户订单（RAG + 工具调用 + 10 条测试集）
- **里程碑**：一个可验收的最小 agent

### 阶段 3 · ERP 刚需（第 7-10 周）
- Ch8 多模态：发票/合同识别流水线（`ir.attachment` → 视觉 API → 结构化）
- Ch1 分类：邮件/工单自动分类
- Ch6 安全：给 agent 加权限白名单（record rules）
- **里程碑**：三个能演示的 AI 功能

### 阶段 4 · agent 上线（第 11-12 周）
- Ch10：建 agent 风险测试集，跑回归
- 补：日志留存、失败兜底、API Key 管理
- **里程碑**：agent 达到可交付状态

### 阶段 5 · 理解与扩展（持续）
- Ch4 / Ch9 / Ch3：理解"为什么这样选方案"
- Ch5 / Ch7 / Ch11：扫读，建立全景认知
