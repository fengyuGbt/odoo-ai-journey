# 逐章发布工作流 · Chapter-by-Chapter Publishing

> 本项目的发布方式：**一章节一章节地往上走**。
> 学一章 → 做实验 → 记踩坑 → 更新笔记 → 提交推送。仓库是"活"的。

## 核心理念

- **小步迭代**：每次推送只含一个章节的产出，一章一个清晰里程碑
- **三件套发布包**：每章推送 = 学习笔记 + 实验代码 + 实践日志
- **踩坑即内容**：真实遇到的问题和解决过程，是社区最看重的部分，
  价值高于完美整理的知识点
- **仓库即学习轨迹**：commit 历史 = 学习过程的可视化记录

## 每章的标准流程（学习 → 发布循环）

```
1. 学习本章（读课程 README + 笔记讲解）
2. 在 Odoo 做对应实验（完成笔记里的"动手任务"）
3. 记录遇到的问题与解决过程（实践日志）
4. 更新笔记：补充实测结果、修正结论、记录数据
5. 提交推送：一章一个 commit（遵循提交规范）
6. 可选：把本章拆成文章，发 dev.to（英文）/ 知乎（中文）
```

## 每章发布包含什么

| 组成 | 位置 | 说明 |
|---|---|---|
| 学习笔记 | `docs/0X-*.md` | 更新"状态"为已完成，补充实测结论 |
| 实验代码 | `odoo/<module>/` | 本章动手任务对应的可运行模块 |
| 实践日志 | 笔记末尾"🛠 实践日志"节 或 `docs/logs/` | 问题现象、排查、解决、教训 |

## 实践日志模板

```markdown
## 🛠 实践日志

### 问题 1：<一句话概括>
- 现象：什么情况下发生了什么
- 排查：试了什么、看了什么（报错、日志、文档）
- 解决：最终怎么解决的
- 教训：下次怎么避免 / 给别人什么建议
```

> 实践日志**不要求等整章完成**——遇到问题解决后可以随时单独提交（`docs/logs/` 下按日期命名，如 `2026-09-15-llm-service-timeout.md`）。

## 发布节奏

| 波次 | 内容 | 触发条件 |
|---|---|---|
| 第 0 波 | 仓库骨架：README + LICENSE + roadmap + 本工作流 | 项目初始化（现在） |
| 第 1 波 | Ch2 笔记（更新版）+ `llm_service` 模块 | Ch2 学完 + 实验跑通 |
| 第 2 波 | 工程三件套 demo（`order_agent`）+ 三件套笔记 | 自然语言查订单 demo 完成 |
| 第 3 波 | Ch8 单据 OCR / Ch1 分类 / Ch6 安全 | 各章按优先级逐个完成 |
| 第 4 波 | Ch10 评估系统 + agent 测试集 | agent 上线前 |
| 持续 | 踩坑记录、读书心得、问答沉淀 | 随时 |

## Git 提交规范

```
feat(odoo): 添加产品描述生成模块
docs(ch2): 补充思维链实测记录
fix(agent): 修复权限绕过漏洞
test(eval): 新增 5 条风险测试用例
chore(repo): 更新发布工作流文档
```

- 一个 commit 只做一件事（笔记 or 代码 or 文档）
- commit message 用英文（开源惯例），正文可加中文说明

## 与文章发布矩阵联动

- 仓库是"内容池"，文章是"放大器"
- 每章笔记完成 → 拆成 1-2 篇文章：
  - 英文 → dev.to（配代码示例）
  - 中文 → 知乎（更口语化）
- 文章里附仓库链接，形成"仓库 → 文章 → 读者回流"的循环

## 常见问题

**Q：笔记还没写完，可以先推吗？**
可以。笔记里用状态标记：⬜ 待学习 / 🔄 学习中 / ✅ 已完成。
半成品 + 诚实的状态标记，比假装完成的文档更受欢迎。

**Q：代码不完整怎么办？**
代码放进 `odoo/` 前先在本地跑通（哪怕是最小可用版）。
仓库里不推"跑不起来"的代码，但可以推"有明确 TODO 的规划"。

**Q：多久推一次合适？**
没有硬性频率。原则：**有实质产出就推**（学完一章 / 解决一个问题 / 写完一篇笔记）。
一周 1-2 次节奏最佳，既保持活跃又不为推而推。
