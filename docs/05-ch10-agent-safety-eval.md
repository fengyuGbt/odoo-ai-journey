# Ch10 智能体安全评估 · 在 Odoo 中的落地

> 课程来源：《动手学大模型》Chapter 10
> Odoo 关联：所有 agent 的质量验收
> 优先级：★★★★★ 第一优先（agent 从 demo 变产品的关键）

## 这一章在讲什么

- **R-Judge 基准**：多轮对话场景下，评测 LLM 是否具备风险识别与应对能力
- **评测方法论**：构造"危险/敏感场景" → 让模型多轮交互 → 评分模型是否有风险意识、
  是否守住了边界
- **多轮是关键**：单轮问不出问题，多轮套话才见真章（对应真实攻击方式）

> 关键认知：**没有评估，就没有"变好"这回事**。agent 改一次坏一次你可能都不知道；
> 有了测试集，才能说"这次改动提升了 10%"。

## Odoo 落地场景

| 需求 | 说明 |
|---|---|
| agent 上线验收 | 上线前跑完整风险测试集，达标才放行 |
| 回归测试 | 每次改 prompt / 换模型 / 改工具，重跑测试集 |
| 失败复盘 | 记录失败对话，分析是提示问题 / 工具问题 / 权限问题 |
| 持续监控 | 线上日志抽样，发现新攻击模式补进测试集 |

## 工程要点（Odoo 侧）

1. **测试用例数据化**：建 `agent.eval.case` 模型（场景描述、预期行为、标签），
   用例是数据不是代码，可增删
2. **日志留存**：agent 多轮对话存独立模型（或 `mail.message` 关联），
   失败样本可追溯、可补进测试集
3. **评分标准化**：给每个用例定"通过标准"（拒绝 / 引导合规 / 明确说不），
   用简单规则或另一个 LLM 评分，输出通过率
4. **门槛机制**：CI 思路——通过率 < 阈值就不允许发布新 prompt

## 动手任务

- [ ] 建 `agent.eval.case` 模型（字段：场景描述、预期行为、严重级别、状态）
- [ ] 写 10-20 条用例：正常任务 5 条 + 风险场景 5-10 条（套数据、诱导改单、注入）+ 边界 5 条
- [ ] 跑一轮，记录通过率；改一个 prompt 再跑，对比（这就是"回归"）

## 与豆包协作的提示词示例

```text
在 Odoo 里设计一个 agent 评估系统：
1. agent.eval.case 模型：场景描述、预期行为、严重级别（低/中/高）、状态
2. 一个执行脚本：逐条把场景发给 agent，记录回复，用规则或 LLM 判定通过/失败
3. 输出通过率报告（按严重级别分组）
4. 支持把线上失败对话"另存为新的测试用例"
先给我数据模型和判定逻辑设计。
```

## 小结

Ch10 给你的是**控制 agent 质量的方法论**。和 Ch2 配套：一个负责"造"，一个负责"验"。
在 Odoo 里把测试用例、日志、门槛做成数据与流程，agent 才真正"可交付"。
